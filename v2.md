## 1. Executive Summary & V2 Vision

GeoDemand AI v1 solved the single-vendor, next-hour operational recommendation problem:
$$\text{GPS Location} + \text{Context} \longrightarrow \text{LightGBM Forecast} \longrightarrow \text{Travel Economics} \longrightarrow \text{STAY vs. MOVE}$$

While v1 successfully proved the viability of hexagonal H3 modeling, quantile uncertainty estimation, and TreeSHAP explainability, **Version 2.0 transforms GeoDemand AI from a reactive single-point advisory tool into an autonomous multi-agent operational operating system for mobile fleets.**

### Core Capabilities Introduced in V2:
1. **Full-Shift Multi-Stop Trajectory Optimization (Vehicle Routing Problem with Time Windows - VRPTW)**: Instead of only looking 1 hour ahead, plan the optimal 8-to-12 hour sequence of locations across a full workday.
2. **Fleet De-confliction & Game-Theoretic Dispatch**: Prevent multiple vendors within the same network or category from cannibalizing each other's footfall.
3. **Closed-Loop Ground Truth Ingestion**: Real-time sales telemetry via UPI QR code webhooks and POS integrations to continuously train and self-correct models.
4. **Cloud-Native Scalability**: Transition from single-node in-memory execution to distributed Redis caching, PostgreSQL/PostGIS spatial persistence, and Kubernetes/ECS container orchestration.

## 3. Phase 1: Multi-Stop Routing & Operations Optimization (`src/optimization/`)

In v1, the model only answers: *"Where should I go for the very next 1 hour?"*  
In v2, populate `src/optimization/` to answer: *"What is my optimal 8-hour shift schedule and driving route from start to finish?"*

### 3.1 Implement Google OR-Tools Shift Planner (`src/optimization/shift_optimizer.py`)
- **Mathematical Formulation**: Vehicle Routing Problem with Time Windows (VRPTW).
- **Inputs**:
  - Shift start time and duration (e.g., 11:00 AM to 10:00 PM, 11 hours).
  - Maximum relocation stops (e.g., 2–4 stops per shift).
  - Minimum dwell time per spot (e.g., 2 hours minimum to amortize setup/parking overhead).
  - Setup and teardown friction (e.g., 20 minutes to pack up equipment and park).
- **Objective Function**:
  $$\max \sum_{k=1}^{K} \left( \text{Revenue}(H_k, t_k, \text{dwell}_k) - \text{COGS} - \text{FuelCost}(H_{k-1} \to H_k) - \text{FixedHourlyCost} \right)$$
- **Deliverables**:
  - `src/optimization/shift_optimizer.py`: Core OR-Tools optimization model.
  - `src/optimization/time_windows.py`: Calculates dynamic demand curve by hour for each candidate cell.
  - API endpoint: `POST /v1/routes/shift-plan`.

## 4. Phase 2: Fleet Coordination & Collision Avoidance

When multiple vendors (either independent subscribers or a corporate food truck fleet) use GeoDemand AI, recommending the same optimal cell to everyone creates **artificial over-saturation** (accidental clustering).

### 4.1 Game-Theoretic Demand Sharing (`src/optimization/fleet_manager.py`)
- **Shared Capacity Model**:
  If Cell $H$ has an expected demand of 60 customers/hr, and Vendor A (Chai Cart) moves there, Vendor B's (identical Chai Cart) marginal expected customer count in Cell $H$ drops by $\approx 50\%$.
- **Dynamic Competition Penalty**:
  Update `competition_score` dynamically based on registered pending reservations:
  $$\text{EffectiveDemand}_i(H) = \frac{\text{BaseDemand}(H)}{1 + \lambda \cdot N_{\text{same\_category}}(H)}$$
- **Soft Hexagon Reservations**:
  - Vendors can "claim" a spot for an upcoming hour via `POST /v1/fleet/reserve-cell`.
  - Other vendors' recommendation rankings automatically downgrade that cell due to increased competition.
- **API Endpoints**:
  - `POST /v1/fleet/dispatch`: Dispatches $M$ food trucks across $N$ candidate zones to maximize fleet-wide total net profit.
  - `GET /v1/fleet/cell-occupancy`: Real-time map of which H3 cells are currently occupied by registered vendors.

## 5. Phase 3: Real Ground-Truth Ingestion & Closed-Loop Telemetry

In v1, the model is trained on a simulated ground-truth dataset because real street-vendor data is proprietary. To make the project 100% complete in the industry sense, v2 introduces **real transaction ingestion**.

### 5.1 Telemetry Ingestion Service (`src/ingestion/`)
- **UPI QR Code & Webhook Adapters**:
  - Webhook listener for payment gateways (Razorpay, Paytm, PhonePe UPI QR) that triggers on customer payments:
    ```json
    {
      "event": "payment.captured",
      "vendor_id": "VND_VIJ_042",
      "timestamp": "2026-11-01T17:15:00Z",
      "amount_inr": 80.0,
      "items": ["tea", "samosa"]
    }
    ```
- **Passive WhatsApp / Telegram Bot**:
  - Simple vendor-facing bot where informal vendors send: `"At Benz Circle, sold 45 cups"` or share their live GPS location pin.
- **Automated Ground Truth Aggregation (`src/data/actuals_aggregator.py`)**:
  - Maps real transactions to corresponding `h3_cell_id` and hourly buckets.
  - Generates `actual_customer_count` to compare directly against $\hat{Y}$ predictions.

## 11. Definition of Done (DoD) for V2

A feature or sprint in V2 is considered **100% DONE** only when:
1. **Code & Typing**: Clean Python 3.11+ code with complete type annotations (`mypy` clean) and zero unused dependencies.
2. **Automated Testing**: Unit and integration tests written with $\ge 90\%$ branch coverage.
3. **No Leakage**: All new temporal signals pass strict anti-circularity verification ($t \to t+1$).
4. **Latency Budget**: Inference and optimization execution completes in $< 150\,\text{ms}$ for single-spot recommendations and $< 1.5\,\text{s}$ for full-shift multi-stop planning.
5. **Observability**: Structured JSON logging, Prometheus metrics, and automated data-drift checks.
6. **Documentation**: Architecture diagrams, updated API schemas in OpenAPI/Swagger, and deployment runbooks included.

### **Complete end-to-end user journey**

1. Vendor registers and creates a business profile.
2. Vendor provides GPS location or manually selects a location.
3. System fetches weather, POI, competitor and demographic context.
4. ML engine predicts next-hour demand and future hourly demand.
5. Decision engine calculates revenue, expenses and expected profit.
6. System ranks suitable H3 cells and calculates travel-adjusted profit.
7. Vendor receives STAY, CONSIDER MOVE or RECOMMENDED MOVE.
8. Vendor requests a complete shift plan if needed.
9. Fleet engine checks occupancy, competition and reservations.
10. Vendor follows the recommended route and receives proactive alerts.
11. Sales transactions are captured through payment or reporting integrations.
12. Actual sales are mapped to H3 cells and hourly buckets.
13. Actual-versus-predicted performance is monitored.
14. Validated data becomes eligible for future model training.
